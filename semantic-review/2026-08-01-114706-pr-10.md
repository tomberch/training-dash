# Xert sync switches from API-parsed activities to FIT download

This change replaces inline activity-and-record creation in `sync_xert_job` with a FIT download approach that delegates parsing to the existing `ingest_job`. Previously, the sync job fetched activity details and session data from Xert's API, manually constructed `Activity` and `Record` rows, and then enqueued route matching. Now it downloads the FIT file from `/activities/download/<path>` and enqueues `ingest_job`, reusing the same ingestion pipeline as manual uploads.

The approach is architecturally cleaner—one parsing path instead of two—and extends the sync window from 30 to 90 days.

Watch for: **Non-`XertAPIError` exceptions during download are swallowed silently** (confirmed)—network timeouts, memory errors, or bugs in the job enqueue call will log nothing and the activity will be skipped without indication of why.

**Verdict**: NEEDS_CHANGES

## High-level view

The sync job no longer builds `Activity` and `Record` rows itself; it downloads a FIT file and hands it to `ingest_job`, which already knows how to parse FIT data and create the corresponding database records. This eliminates duplicate parsing logic and ensures Xert-sourced activities go through the same validation as uploaded files.

Error handling narrowed during the refactor. The old code caught both `XertAPIError` and generic `Exception` when processing each activity; the new code catches only `XertAPIError`. A transient failure in `pool.enqueue_job()` or an unexpected exception from httpx would skip the activity with no log entry.

<summary>Details</summary>

### Exception scope narrowed during refactor

The old `sync_xert_job` loop had two exception handlers:

```python
except XertAPIError as e:
    logger.warning(f"sync_xert_job: Failed to import activity {xert_activity.id}: {e}")
    await db.rollback()
    continue
except Exception as e:
    logger.warning(f"sync_xert_job: Error importing activity {xert_activity.id}: {e}")
    await db.rollback()
    continue
```

The new code removes the generic handler:

```python
except XertAPIError as e:
    logger.warning(f"sync_xert_job: Failed to download activity {xert_activity.id}: {e}")
    continue
```

`XertAPIError` wraps HTTP status errors and connection errors, but it does not cover every failure path. `pool.enqueue_job()` can raise if Redis is unreachable mid-loop (the pool was created successfully, but the connection died). `httpx` can raise `httpx.TimeoutException` separately from `httpx.RequestError` in some configurations. In all these cases the activity is silently skipped with no log message.

The removal of `await db.rollback()` is correct (no database writes happen in the new flow), but the removal of the catch-all exception handler is an oversight. Recommend restoring:

```python
except Exception as e:
    logger.warning(f"sync_xert_job: Unexpected error for activity {xert_activity.id}: {e}")
    continue
```

Not tested: behavior when `pool.enqueue_job()` raises. The test `test_sync_xert_continues_on_download_failure` confirms continuation past `XertAPIError`, but not other exception types.
