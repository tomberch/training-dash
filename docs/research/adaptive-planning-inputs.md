# Adaptive planning inputs — what sustainable training/nutrition plans actually need

> Research ticket #709 (parent #706). Feeds the Athlete Snapshot definition decision in #713.
> Date: Sep 30 2026.
> Method: primary sources only — first-party docs (TrainerRoad support, TrainingPeaks help/blog, Garmin owner's manuals + Garmin Technology pages, whoop.com, Garmin Developer Program), and peer-reviewed literature (MDPI/Int J Environ Res Public Health, Sports Medicine–Open, J Appl Physiol, BJSM/IOC). Vendor blog/marketing pages are cited as vendor claims, not independent evidence. Repo facts verified against `backend/src/trainingdash/integrations/garmin/client.py` and `backend/migrations/versions/001_initial_schema.py`.

## Summary

- **TrainerRoad's adaptive engine deliberately uses *zero* daily wellness inputs.** Red Light Green Light / AI Training Simulation is driven by training load history and post-workout RPE surveys only ([Fatigue Detection](https://support.trainerroad.com/hc/en-us/articles/20753792083995-Red-Light-Green-Light), [AI Training Simulation](https://support.trainerroad.com/hc/en-us/articles/41652509070619-How-to-use-AI-Training-Simulation)). Sleep/recovery data are explicitly *not* integrated (a long-running user request: [forum thread](https://www.trainerroad.com/forum/t/product-suggestion-incorporating-sleep-recovery-data-into-adaptive-training-season-planner-red-light-green-light/93979)). TrainingPeaks is the opposite: wellness is a **manual-entry** metric layer (30+ fields; sleep hours/quality, HRV, RHR, stress, soreness, fatigue, mood, hydration) that coaches read manually rather than an algorithm consumes automatically ([Metrics how-to](https://help.trainingpeaks.com/hc/en-us/articles/204072364-TrainingPeaks-Metrics-How-to-enter-Weight-HRV-Sleep-etc), [available metrics](https://help.trainingpeaks.com/hc/en-us/articles/360025290131)).
- **Whoop and Garmin consume objective recovery inputs**: HRV, RHR, respiratory rate, sleep duration/consistency, (Whoop) sleep performance vs. need; (Garmin) sleep score, sleep history 3 nights, HRV status, acute load, recovery time, stress history 3 days. Garmin's own Training Readiness formula is documented in device manuals and is the closest published template for an integrated readiness score ([fēnix manual](https://www8.garmin.com/manuals/webhelp/GUID-708A8F4D-9A78-49CF-9528-DE109BBCC472/EN-US/GUID-C21BE0C8-A08E-4DA1-B6C6-2E0E2DDDB372.html)).
- **Cycle phase is NOT a proven training-modulation input.** A 2025 systematic review restricted to hormone-verified studies found inconsistent, mostly absent phase effects on performance ([J Appl Physiol 2025](https://pubmed.ncbi.nlm.nih.gov/40695607/)); expert guidance favors a **symptom-informed** approach over phase-based ("cycle syncing") training ([CASES expert statement](https://www.cases.org.uk/imgs/cases_tses_winter_2025___expert_statement478.pdf)). If supported, track cycle data as *context/flagging* (and as a menstrual-function REDs indicator), never as an automatic plan modifier.
- **Almost every objective recovery input is already fetchable through our existing Garmin connection at zero marginal acquisition cost.** The repo uses the `garminconnect` Python library (v0.3.10, credential login — the same approach as our current activity/FIT sync), which exposes `get_sleep_data`, `get_hrv_data_range`, `get_rhr_daily`, `get_body_composition`, `get_steps_data`, `get_stress_data`, `get_training_readiness`, `get_lifestyle_logging_data`, and menstrual data endpoints ([README/demo](https://github.com/cyberjunky/python-garminconnect), [typed.py models](https://github.com/cyberjunky/python-garminconnect/blob/master/garminconnect/typed.py)). The only *policy* risk is that these are unofficial Garmin Connect web endpoints, not the sanctioned Garmin Health API (partner-only, approval-gated: [Garmin Developer Program](https://developer.garmin.com/gc-developer-program/overview/)). Mitigation: wrap each call in our existing `GarminClient` protocol with mock + typed models, tolerate fields disappearing, and keep the DB raw (store the metric value, not the endpoint shape).
- **The evidence-based ceiling for "sustainable" planning is modest**: trends, not single days (7-day rolling averages vs. personal baseline), and the two highest-value additions per the literature are sleep and energy-availability proxies (weight trend + menstrual function flags), not more exotic metrics ([Plews review in PMC HRV S&C guidance](https://pmc.ncbi.nlm.nih.gov/articles/PMC11204851/), [IOC REDs 2023](https://bjsm.bmj.com/content/bjsports/57/17/1073.full.pdf)).

## Prioritized input list (with acquisition cost)

Cost code: **$0** = via existing `garminconnect` login we already persist (activity list + FIT); **$0\*** = same library but *unofficial* endpoint (no SLA, may break; device-dependent availability); **manual** = user self-report (we have a metrics API already; no new acquisition code, only UI); **paid** = requires a separate vendor API/device integration.

| # | Input | Why (what it feeds) | Who consumes it | Acquisition cost |
|---|-------|--------------------|-----------------|------------------|
| 1 | **Sleep duration (h) + sleep history (3-night trend)** | Largest non-training recovery input; sports-science weight (injury/sick correlation, e.g. Milewski 2014 via [Whoop coaches manual](https://wecoachsports.org/wp-content/uploads/whoop-coaches-manual.pdf)); feeds coach-AI "back off" logic | Whoop (sleep performance vs. need), Garmin (sleep score + 3-night history), TrainingPeaks (manual `sleep_hours`) | $0 via `get_sleep_data` in garminconnect (already installed). Needs a nightly sync job + one `sleep_hours` metric-type row |
| 2 | **Resting HR (RHR), nightly/trend** | Cheap, validated recovery marker; rising RHR → overreaching/illness (Whoop; [TrainingPeaks "5 signs"](https://www.trainingpeaks.com/blog/5-signs-you-need-to-adjust-your-training-load/)) | Whoop, Garmin (auto), TrainingPeaks (manual) | $0 via `get_heart_rates` / `get_rhr_daily`. Already in our metric seed list (`restinghr`, `allowed_sources: ['manual','device']`) — just wire source `device` |
| 3 | **HRV — 7-day rolling average vs. personal baseline, not daily values** | HRV-guided training improves VO2max vs. fixed plans (small ES, [MDPI meta-analysis](https://www.mdpi.com/1660-4601/17/21/7999)); daily values are noisy; rolling 7-day vs. baseline is the guideline-recommended use ([PMC review](https://pmc.ncbi.nlm.nih.gov/articles/PMC11204851/), [Plews 2013]) | Whoop (rMSSD during SWS), Garmin (overnight "HRV Status" with personal baseline + status word balanced/unbalanced/low/poor, needs 3 weeks of wear) | $0 via `get_hrv_data_range`. Must compute the baseline ourselves (or consume Garmin's status word) — real implementation cost is the rolling-window logic, not acquisition |
| 4 | **Athlete weight / weigh-in trend** | Already in scope in the ticket; required for W/kg, and the *trend* (downward drift + symptoms) is the cheapest LEA/REDs screening signal ([IOC REDs 2023](https://bjsm.bmj.com/content/bjsports/57/17/1073.full.pdf)) | TrainingPeaks (chart-critical), Garmin (body composition), Whoop (not a primary input) | $0 via `get_body_composition` / `get_weigh_ins`; already a seeded metric type (`weight`) |
| 5 | **Garmin Training Readiness score (optional shortcut)** | Pre-computed composite of sleep score, HRV status, sleep history, acute load, recovery time, stress history — Garmin has already done the integration work we'd otherwise build ([fēnix 9 manual](https://www8.garmin.com/manuals/webhelp/GUID-708A8F4D-9A78-49CF-9528-DE109BBCC472/EN-US/GUID-C21BE0C8-A08E-4DA1-B6C6-2E0E2DDDB372.html)) | Garmin only | $0\* via `get_training_readiness` / `get_morning_training_readiness` (0.3.10 supports both). Availability varies by watch model — must be treated as nullable |
| 6 | **Perceived recovery / soreness / stress (self-report, 3-boolean or 1–5)** | The only subjective input coaches verifiably act on; cheap; captures "90% of the day" that load metrics miss (mental-fatigue evidence: [TrainingPeaks lifestyle factors](https://www.trainingpeaks.com/coach-blog/lifestyle-factors-adding-to-training-load/)); IOC REDs flags mood/illness as primary secondary indicators | TrainingPeaks (whole model is manual-entry), Whoop (Journal), *not* TrainerRoad | manual — no new acquisition code; reuse existing `/me/metrics` API; cost = UI for a daily "check-in" |
| 7 | **Energy availability proxy — weight trend + training energy expenditure (kcal) vs. intake estimate** | Core of REDs screening; direct EA measurement is infeasible outside labs, so the *minimal* practical monitoring set is body composition + menstrual function + fatigue scales ([IOC/2023](https://bjsm.bmj.com/content/bjsports/57/17/1073.full.pdf); [Nutrients 2026 review](https://pmc.ncbi.nlm.nih.gov/articles/PMC12899827/)) | Intervals.icu/TrainingPeaks ecosystem tools (indirectly), coach (manually) | $0 for expenditure (already have activity kcal via Garmin), $0\* for body composition. Intake is **manual entry only** — do not auto-estimate |
| 8 | **Cycle phase / menstrual function (if applicable)** | Tracking menstrual dysfunction is a low-cost, sensitive LEA indicator in females ([IOC REDs](https://bjsm.bmj.com/content/bjsports/57/17/1073.full.pdf)); *but* phase-based training modulation is not evidence-supported — use for context, symptom flagging, and REDs screening only ([J Appl Physiol 2025](https://pubmed.ncbi.nlm.nih.gov/40695607/); [CASES 2025](https://www.cases.org.uk/imgs/cases_tses_winter_2025___expert_statement478.pdf)) | Garmin (device-side MCT), Whoop, TrainingPeaks (manual); Garmin Health exposes it too (partner-only) | $0\* — Garmin Connect menstrual data is available on the same unofficial endpoints used by `garminconnect`-style clients (e.g. `get_menstrual_data`, `get_menstrual_calendar_data` in [garmin-health-data](https://github.com/diegoscarabelli/garmin-health-data); official [Garmin Women's Health API](https://developer.garmin.com/gc-developer-program/womens-health-api/) is partner-only). Highly sensitive data — opt-in toggle required |
| 9 | **Steps / NEAT / lifestyle stress load** | Secondary; captures the non-training 90% of the day for total-load context (TrainerRoad forum criticism; Whoop's whole pitch) | Whoop (day strain), Garmin (steps, stress, body battery) | $0\* via `get_steps_data`, `get_all_day_stress`, `get_body_battery` |
| 10 | **Respiratory rate, SpO2, sleep-stage breakdown, body battery, hydration, nutrition logging** | Low marginal signal for *plan modulation* vs. #1–#3; useful for illness detection in later iterations (Whoop uses resp. rate mainly as a sickness flag) | Whoop, Garmin only; TrainingPeaks manual | $0\* for the device-data subset; **paid/manual** for real nutrition intake (no reliable source — see gaps) |
| 11 | **Blood biomarkers (testosterone, T3, iron, BMD, etc.)** | The proper way to confirm LEA/REDs, but needs labs + physician; explicitly outside app scope for now ([Nutrients 2026](https://pmc.ncbi.nlm.nih.gov/articles/PMC12899827/)) | Coaches with doctor support | **paid/manual** — out of scope |

## What each platform actually consumes (vendor-by-vendor)

- **TrainerRoad** — load-history + RPE only; no wellness/device inputs. Explicit stance that RLGL "is not a readiness score" and is *predictive* from load, not reactive from recovery ([support](https://support.trainerroad.com/hc/en-us/articles/20753792083995-Red-Light-Green-Light), [press](https://bicycleretailer.com/announcements/2024/03/20/introducing-red-light-green-light-next-generation-fatigue-management)).
- **TrainingPeaks** — everything is *coach-facing manual entry* (weight, HRV, sleep hours/quality, RHR, stress, soreness, fatigue, mood, hydration, urine color, percent fat, muscle mass, sleep elevation, overall feeling, etc., 30+ metrics). No documented algorithm consumes these; they feed dashboards/PMC overlays ([metrics how-to](https://help.trainingpeaks.com/hc/en-us/articles/204072364-TrainingPeaks-Metrics-How-to-enter-Weight-HRV-Sleep-etc), [available metrics](https://help.trainingpeaks.com/hc/en-us/articles/360025290131), [HRV blog](https://www.trainingpeaks.com/blog/how-to-track-your-heart-rate-variability-using-trainingpeaks/)).
- **Whoop** — Recovery = HRV (rMSSD during SWS) + RHR + respiratory rate + sleep performance vs. need, all vs. personal rolling baseline. Day Strain adds 24/7 non-workout load. Journal captures *behavioral* modifiers (alcohol, late meals, melatonin) ([How Recovery works](https://www.whoop.com/us/en/thelocker/how-does-whoop-recovery-work-101/), [coaches manual](https://wecoachsports.org/wp-content/uploads/whoop-coaches-manual.pdf)).
- **Garmin** — Training Readiness = sleep score (last night) + recovery time + HRV status + acute load + sleep history (3 nights) + stress history (3 days); Training Status is load-based. Inputs come from the device, not from user questionnaires ([fēnix 9 manual](https://www8.garmin.com/manuals/webhelp/GUID-708A8F4D-9A78-49CF-9528-DE109BBCC472/EN-US/GUID-C21BE0C8-A08E-4DA1-B6C6-2E0E2DDDB372.html)).

## What's reachable through our existing Garmin connectivity, at what cost

**Code reality check:** `backend/src/trainingdash/integrations/garmin/client.py` currently implements only `login`, `complete_mfa`, `list_activities`, `download_fit`, `upload_fit` via the `garminconnect` library (`garminconnect>=0.2.25`, installed 0.3.10). **No wellness endpoints are consumed today.** The existing `metric_types` seed (`weight`, `restinghr`, FTP, LTHR, HRmax) already anticipates `device` and `recovery` sources — so the schema has room; only rows + sync jobs are missing.

Reachable **without buying anything and without Garmin Developer Program approval** (unofficial Connect web API, via the same credentials we already use):

| Endpoint (garminconnect 0.3.10) | Gives us | Official alternative | Official access |
| --- | --- | --- | --- |
| `get_sleep_data` | duration, stages (deep/REM/light/awake), sleep score components, `avgSleepHRV`, resp. rate, SpO2 | Health API `sleep summaries` | Partner-only approval ([dev program](https://developer.garmin.com/gc-developer-program/)) |
| `get_hrv_data_range` / `get_hrv_data` | nightly rMSSD + Garmin's own baseline | — | Not exposed via official API |
| `get_rhr_daily` | nightly resting HR | Health API dailies | Partner-only |
| `get_body_composition` / `get_stats_and_body` | weight, BMI, body fat %, muscle mass | Health API body composition | Partner-only |
| `get_steps_data`, `get_all_day_stress` (incl. body battery), `get_training_readiness` | NEAT, stress load, pre-built readiness | Health API dailies / stress details | Partner-only |
| Menstrual data (via periodic-health endpoints used by ecosystem wrappers) | cycle day, phase, flow, symptoms, predictions | Women's Health API | Partner-only approval |

**Cost verdict:** item-by-item acquisition cost is effectively **$0 in money** for #1–#5, #8–#9 above; the real cost is (a) engineering for unofficial-endpoint brittleness (typed wrapper models like `SleepData`, `HrvData | None` already exist in 0.3.10's `typed.py` and are the right shape to wrap in our `GarminClient` protocol / `mock_client.py`), (b) privacy work for opt-in of sensitive (#8) data, and (c) **manual** for nutrition intake and subjective check-ins. Real **paid** cost would only arise if we wanted an SLA-backed official API — that path (Garmin Health / Women's Health) is gated, evaluation-environment-only, and worth pursuing only if the unofficial surface proves load-bearing in the coach AI.

## Recommended MVP vs. later split

### MVP (coach-AI Athlete Snapshot v1) — highest evidence-per-cost
1. **In-body already**: FTP/LTHR, trained load (CTL/ATL/TSB), weight trend. (Just keep.)
2. **Sleep duration + 3-day sleep history** via `get_sleep_data` (nightly sync job → `sleep_hours` metric, `source: device`).
3. **RHR trend** via `get_rhr_daily`/daily heart rates → existing `restinghr` metric, `source: device`.
4. **HRV: 7-day rolling average + "vs. personal baseline" flag** via `get_hrv_data_range`. Do *not* put daily HRV values in front of the coach AI; use the flag only ([PMC guideline](https://pmc.ncbi.nlm.nih.gov/articles/PMC11204851/)).
5. **Self-report daily check-in** (1–5 energy/mood/stress/soreness) reusing `/me/metrics` (manual; no new acquisition).
6. **Guardrail** — never surface a single "readiness" decision to the AI from one metric; require *converging* signals (sleep low AND RHR up) before flagging (aligns with Plews/Buchheit guidance and Whoop's own finding that integrated recovery beats single metrics).

Explicitly **deferred from MVP**: steps/NEAT, body battery, SpO2/respiratory detail, nutrition intake, cycle phase-based modulation, blood biomarkers.

### Later (phase 2+)
- Garmin **Training Readiness** passthrough (device-computed shortcut; nullable for older watches).
- **Menstrual/cycle data** as *opt-in, context-only + REDs screening input* — never as an automated training modulator (evidence does not support phase-based training).
- **Body composition** (fat %, muscle mass) for physique-trend work beyond weight alone.
- **Nutrition intake**: keep manual; consider an optional paid partner integration only if a user segment demands it.
- **Blood biomarkers / REDs formal screening questionnaires**: clinician-supported flow, out of product scope.
- **Official Garmin Health API** migration if the unofficial endpoints break or if we need SLAs.

## Risks / gaps / unverified

- **Unofficial endpoints**: everything above "works" via credential-logged web API; Garmin does not contractually guarantee these methods. Mitigation: defensive typing (0.3.10 `typed` models tolerate `None`), fallback to manual entry for every one of these inputs (we already have `/me/metrics` for manual).
- **Device dependence**: HRV status and Training Readiness require specific Garmin watches and ~3 weeks of adaptation data; body-temperature-based cycle tracking varies. The Athlete Snapshot must treat all of these as `nullable`.
- **Intake accuracy**: real EA (energy-in vs. out) is not reliably measurable outside labs ([Nutrients 2026](https://pmc.ncbi.nlm.nih.gov/articles/PMC12899827/)). Do not claim EA compliance in the snapshot; at best surface *reported* intake vs. *estimated* expenditure with a clear disclaimer.
- **Whoop/TrainerRoad acquisition**: if we ever want Whoop data, that's a paid OAuth integration (Whoop API); TrainerRoad has no adaptive-input API — this research deliberately scopes around that.
