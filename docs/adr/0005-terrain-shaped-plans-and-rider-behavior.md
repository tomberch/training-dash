# Terrain-Shaped Plans and Rider-Behavior Learning

Status: Accepted

Extends ADR 0004. Decisions below came out of the plan-vs-reality investigation
(plan 13 / activity 59f1b2eb) and a design grill.

## Context

Plan 13 (time-targeted) promised avg 174W / NP 175W / "never more than 186W" for a
90-minute ride the rider actually completed at avg 184W / NP 239W (VI 1.30). Diagnosis:

1. **Mode A (time-targeted) minimizes energy at fixed time**, which converges to
   near-constant power (VI 1.005). Constant power is energy-optimal but
   physiologically fictional — real riding on variable terrain has VI 1.2–1.3,
   so real NP at the same average is 25–35% higher. Wrong objective, not a
   physics error. Mode A also ignores the rider's learned coefficients and
   ride type stops only pad the clock.
2. **The calibrated grade-power coefficients are poisoned**: the climb fitter
   normalizes power by whole-ride average *including 0W coasting*, inflating
   intercept (1.30 vs ~1.10) and crushing slope (0.02, R²=0.009). Plans built
   on them pedal hard downhill and are also nearly constant power.
3. **`descent_power_multiplier` (coasting on descents) is stored but dead at
   runtime** — the coefficient designed to encode coasting behavior is
   consumed by no code path.
4. Ride types (race/gran_fondo/training/touring) already encode intended ride
   character (`stop_pct`, `descent_aggressiveness`) but barely influence the
   generated plan. Measured rider behavior is terrain-dependent (rolling ~1%
   coast/stops, hilly ~16%, mountain ~19%) and learnable from records — but
   activities carry no race/training tag, so learning must produce a *baseline*
   that plan type then modulates.

## Decision

**1. One terrain-shaped engine, two inputs.** Every default plan is generated by
the fine-grained terrain-adapted engine with the rider's learned profile. The
profile produces a *shape* (power distribution over the course given terrain,
coasting, stops); the request then supplies one of:

- **target intensity** → shape applies directly; time is an output (today's Mode C), or
- **target time** → the shape is *scaled* (on pedaling segments; descents stay
  at coasting level) until riding time hits the target; NP/avg are honest
  outputs of the scaled shape.

A plan no longer minimizes energy. `optimize_pacing_for_time` (constant-power
time solver) is deleted. Mode B (`optimize_pacing`, energy-budget with W'bal)
survives as an explicit opt-in "what would optimal pacing look like" tool.

**2. Sustainability traffic light.** Every plan carries a sustainability level
computed from required intensity vs the rider's capability (IF, W'bal depth):
green = sustainable, yellow = very hard (near-limit), red = beyond capability.
Red plans are still generated and saved, flagged — only a *physically
impossible* request (scale exceeding solver bounds, e.g. time faster than
max-power-flat-out) is a hard error.

**3. Rider-behavior learning.** The learning loop fits, per rider (and bike
where meaningful):

- `descent_power_multiplier`: fraction of base power held while descending
  (coasting behavior) — becomes live in the fine-grained engine on descents.
- stop/coast baseline: fraction of ride time not pedaling (complete stops +
  coasting), derived from cadence/speed records, reported per terrain type.

Ride type (race/gran_fondo/training/touring) **modulates** this baseline via
preset factors: training = baseline as-is; race/gran_fondo push coasting down
and stops down; touring pushes both up. Presets ship constants first; they may
become learned later. Activities carry no race tag, so this split (learned
baseline + plan-type modulation) is the only workable design.

**4. Calibration normalization fix + quality gate.** The grade-power fit uses
power samples *while pedaling only*, normalized by pedaling-time average —
coefficients describe pedaling shape; coasting is the multiplier's job. Coeffs
are stored only if fit quality passes a gate (R² floor + sample counts);
otherwise prior coefficients are kept and the API's existing `confidence`
mechanism reports it. On deploy of the normalization fix, stored coefficients
are invalidated once and flagged for recalibration (they cannot be trusted).

**5. Learning-loop extension.** `a_lat` (shipped), intercept/slope (refit),
`descent_power_multiplier`, and stop/coast baseline join the same feedback
loop with the same quality gate. `descent_power_multiplier` loses its dead
status and is consumed at runtime like every other coefficient.

## Consequences

- Plans become comparable to real rides: same avg and terrain → same NP within
  the validated error bars. "Never more than 185W" fantasies disappear; a hard
  target time shows up as a yellow/red flag instead of hidden in constant watts.
- The scipy optimizer path shrinks to opt-in Mode B; the energy-minimization
  objective is no longer used for default plans.
- Recalibration is required after deploy (old coefficients invalid); plans
  generated before recalibration fall back to defaults with a warning.
- Ride-type presets gain modulation semantics: choosing "race" vs "touring"
  now changes the power plan, not just the clock margin.
- Time-targeted plans scale the rider's own shape — no negative-split/attack
  strategies. Those remain in opt-in Mode B only.

### Before/After: The NP Fiction is Closed

The original plan-13 failure showed plan-VI ≈ 1.0 vs actual VI ≈ 1.30 — a 30%
gap that made NP predictions meaningless. After ADR 0005:

| Course type | Actual VI (mean) | Predicted VI (mean) | VI error |
|-------------|-----------------|---------------------|----------|
| Hilly (n=20) | 1.18 | 1.12 | 5.8% |
| Mountain (n=10) | 1.32 | 1.26 | 4.8% |

Plans now produce terrain-shaped power distributions with realistic VI, so
predicted NP tracks actual NP within the validated error bars.
